# CLI setup, Planner hosts, and Executor models

This is the human-facing guide for managed A2A setup (A6). Every file is
generated by `handoff`; nothing here asks you to write or edit JSON. The
sequence below is the one the tests and the live check exercise
([evidence](qa-a6-cli-usability.md)).

## 1. One-time runtime

```sh
export PATH="$HOME/Documents/GitHub/handoff-automation/bin:$PATH"
(cd ~/Documents/GitHub/handoff-automation && uv sync)
```

`handoff` finds the A2A runtime as `HANDOFF_A2A_BIN`, then `handoff-a2a` on
`PATH`, then this checkout's `.venv/bin/handoff-a2a`. If none exists it prints
the `uv sync` command above; it never downloads anything itself. Provider
CLIs are found on `PATH` or through `HANDOFF_CLAUDE_BIN`, `HANDOFF_CODEX_BIN`,
`HANDOFF_CURSOR_BIN`. Logins stay yours: `claude /login`, `codex login`,
`cursor-agent login` for the Executor account.

## 2. See which models exist

```sh
handoff models "/path/to/project" --provider cursor
handoff models "/path/to/project" --provider codex
handoff models "/path/to/project" --provider claude
```

| Provider | Discovery | What it proves |
|---|---|---|
| cursor | `cursor-agent models` (requires login) | Models this account can use from the CLI, including Grok IDs such as `grok-4.7-high` when the account exposes them. The editor's model picker is not evidence of CLI access. |
| codex | `codex debug models` | The installed CLI's catalog, not account entitlement. An ID outside it is accepted as *unverified*; a rejection shows up as a provider error on the run. |
| claude | none | The Claude CLI has no enumeration. Any explicit provider-native ID is accepted as *unverified*. |

No list is hardcoded, and no model is ever substituted for another.

## 3. Set up a repository

On a terminal, `handoff init "/path/to/project"` asks for:

1. transport (`a2a`, or `legacy` for the original Python-free direct-Claude path);
2. Executor provider;
3. Executor model (it shows the provider's own list; type an ID or a list number);
4. Planner host integration (`cursor` or `none`).

Scripted (quote paths; model IDs, including bracketed parameters such as
`'claude-opus-4-8[effort=high]'`, are passed through unchanged):

```sh
handoff init "/path/to/project" --transport a2a --executor cursor --model "grok-4.7-high" --planner cursor
handoff init "/path/to/project" --transport a2a --executor codex  --model "gpt-5.6-luna" --reasoning-effort medium
handoff init "/path/to/project" --transport a2a --executor claude --model "<your Claude model ID>"
handoff init "/path/to/project" --transport legacy
```

In a non-interactive shell, bare `init` on a new repository prints these
commands and changes nothing. Model and login checks run before anything is
written, and a failure writes nothing.

What it creates (all machine-local and git-excluded through
`git rev-parse --git-path info/exclude`, so linked worktrees work):

| Path | Contents |
|---|---|
| `.handoff-config.json` | client routing: endpoint URL, workspace ID, token path, and a `managed` pointer to `server.json` |
| `.handoff-logs/server.json` | the authoritative Executor selection (`claude`/`codex`/`cursor` block, `config_generation`, validation provenance), port, paths |
| `.handoff-logs/credentials/service-token` | random local bearer token (mode 0600, directory 0700). Never printed, never in argv or evidence |
| `.handoff-logs/server-evidence/` | server state database and per-run evidence |
| `.handoff-logs/service/` | process record, server logs, lock, queued selection, `history.jsonl` |
| `HANDOFF.md` | the protocol template, only if absent |
| `.cursor/skills/handoff-cli/` | only with `--planner cursor`: a project-local copy of the Planner skill |
| `.claude/settings.local.json` | only for the Claude Executor: the permission allowlist (`handoff permissions`) |

Re-running `init` keeps the plan, token, selection, approval and history,
and your settings. Asking for a different model through `init` is refused
with the `handoff model` command to use instead. A tracked or symlinked
target, a malformed config, or an unrelated `.cursor/skills/handoff-cli` is
refused, and any files the failed attempt created are removed.

**Existing repos.** Bare re-init changes nothing but the excludes. A manually
configured endpoint keeps working for `execute`/`resume`/`status`/`cancel`,
but managed `server`/`model` commands refuse to touch it. To migrate, run
`init --transport a2a --executor ... --model ...`. Migration refuses while a
run is unresolved, keeps the old workspace ID so approval receipts still
match, saves the old config under `.handoff-logs/service/backups/`, and never
deletes external credentials or databases.

## 4. Start the local service

```sh
handoff server start  "/path/to/project"
handoff server status "/path/to/project"
handoff server stop   "/path/to/project"
```

`start` runs `handoff-a2a serve` as a child in its own session, which
outlives the command. There is no LaunchAgent or other OS-wide daemon. A
server only counts as running once its Agent Card names this workspace, the
selected provider/model, and `config_generation`, and an authenticated probe
with the token succeeds. A matching port alone is never enough.

- Starting again when it is already verified is a no-op.
- If a process this CLI did not start holds the port, nothing is stopped.
  Use `handoff server start "<repo>" --port <free-port>` to move the idle
  service.
- A stale process record (dead PID, or a reused PID with another start
  identity) is discarded and never signaled.
- `stop` refuses while a run is outstanding, a submission is in progress,
  `execute.lock` is held, or the server database has a non-terminal execution.
- If a start does not verify, the child it launched is stopped and
  `last-failure.json` is written. `execute`/`watch` then refuse to dispatch
  until a verified service is running.

`init` never starts the service, and `watch` never starts it for you.

## 5. Plan with Cursor (or any Planner)

- **Cursor editor:** choose the Planner model in the chat model picker, stay
  in Agent mode (Plan/Ask modes are read-only and cannot write the DRAFT),
  and type `/handoff-cli plan ... in the handoff`. Customize > Skills lists
  `handoff-cli` once it is discovered.
- **Cursor CLI:** `handoff planner "/path/to/project" --provider cursor --model "<id>"`
  checks the model against `cursor-agent models` and opens an interactive
  `cursor-agent --model <id> --workspace <repo>` session. Type `/handoff-cli`
  there. The launcher never approves, dispatches, or reads the session's exit
  as approval. Add `--print-command` to see the command without starting it.
- The Planner's model is chosen in its own host and never changes the
  Executor selection or a running task.

Flow: the Planner writes a `DRAFT` and stops. After you approve in chat,
`handoff approve` records the receipt; then `handoff watch` or
`handoff execute` dispatches. QA is the Planner reviewing the actual diff and
running the tests; merging stays with you.

## 6. Change the Executor model within a workflow

```sh
handoff model "/path/to/project"                                          # selected / active / current run / pending
handoff model "/path/to/project" --provider cursor --model "composer-2.5"  # now (between executions)
handoff model "/path/to/project" --provider codex --model "gpt-5.6-luna" --reasoning-effort medium --after-current
handoff model "/path/to/project" --cancel-pending
```

- **Now.** The candidate is validated first. Then, holding the service lock
  and the submission lock, the CLI checks that nothing is outstanding, stops
  the owned server, writes the new `server.json` (next `config_generation`),
  starts it again on the same port and database, and verifies it. The
  workflow ID, approved plan hash, round count, dispatch hold, branch/HEAD,
  and continuation fingerprint are unchanged. A running `watch` picks up the
  new selection at its next dispatch; there is no need to restart it. If the
  service is stopped, the selection is saved for the next `server start`.
- **During a run** the immediate form refuses. Use `--after-current`, or
  `handoff cancel` and review. `--after-current` records a validated pending
  selection and leaves the live service, the current run, and its saved
  endpoint alone. `watch` (as soon as the run is reconciled) or the next
  `execute` applies it once, before a new worker starts. Repeating the same
  request is a no-op; a different request replaces the pending one (recorded
  in `history.jsonl`).
- **Failures.** If the new service does not start, the previous `server.json`
  is restored and restarted, and the failure is recorded. A queued change
  that fails is kept, marked failed, and blocks dispatch until you replace it
  or run `--cancel-pending`. A queued change stays queued while ownership is
  uncertain (outstanding run, unknown acknowledgement, recovery required).
  Applying a selection never clears a dispatch hold or refills rounds.
- **Plan constraints.** If the approved Current Task contains an
  `**Executor:** provider / model` line, a different selection is refused:
  changing that requirement needs a revised, re-approved plan.
- **Evidence.** Every run records the identity it was submitted to (provider,
  model, generation) plus, for Cursor, the model the CLI reported. See
  `handoff runs` (EXECUTOR column), manifests, and `handoff status`. Later
  switches never rewrite these records.

Switching never moves a conversation that is in progress. To interrupt a run:
`handoff cancel`, review the partial Git changes, then execute again under
the same history rules.

## 7. Recovery quick reference

| Symptom | Next step |
|---|---|
| `dispatch deferred: ... not running the selected Executor` | `handoff server status`, then `handoff server start` |
| `queued Executor change ... failed` | `handoff model ... --after-current` (replace) or `--cancel-pending` |
| `cannot switch now: an A2A run is outstanding` | `handoff status` / `resume` / `cancel`, or `--after-current` |
| `port N is in use by a process this CLI did not start` | `handoff server start "<repo>" --port <free>` |
| `Cursor CLI is not logged in for the Executor` | `cursor-agent login` (Executor account), then retry |
| `this repository has no CLI-managed A2A service` | `handoff init "<repo>" --transport a2a --executor ... --model ...` (explicit migration) |

## 8. Cursor Executor details and limits

- Cursor's print mode applies edits and runs shell commands only with
  `--force`. The adapter pairs it with a per-run `CURSOR_CONFIG_DIR`: deny
  rules for `git push/merge/remote`, `gh`, `handoff`, `handoff-a2a`, and
  nested agents, plus Cursor's sandbox with an empty network allowlist for
  shell commands. Your global `~/.cursor/cli-config.json` is neither read nor
  changed, and MCP servers are not auto-approved. The deny rules are Cursor's
  best-effort command matching (`git push` and `git <options> push` forms are
  listed); what actually stops a push or PR is the sandbox's empty network
  allowlist for shell commands.
- Every Executor adapter (Claude, Codex, Cursor) strips inherited `CURSOR_*`
  variables, so a server started from a Cursor Planner shell never passes
  that session's variables to a worker. The Cursor Executor gets only its
  own per-run `CURSOR_CONFIG_DIR` (plus `CURSOR_API_KEY` when a server-side
  `api_key_file` is configured).
- User-level Cursor content that the CLI loads from your home directory
  (`~/.cursor/rules`, `~/.cursor/skills`, `~/.agents/skills`, and the MCP
  server list) is not isolated. The delivery rule states the Executor role,
  and the deny rules stop recursive `handoff` dispatch. Review user-level
  skills that match "handoff" if a run goes off course.
- The HANDOFF snapshot reaches Cursor as a temporary always-applied rule
  `.cursor/rules/handoff-executor-<execution_id>.mdc`, alongside AGENTS.md
  and existing rules, and is removed when the worker stops. The live check
  confirms Cursor loads it (see the evidence).
- Cursor reports no price; `cost_usd` stays `null`.
